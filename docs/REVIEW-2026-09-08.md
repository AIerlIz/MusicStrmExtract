## 职责边界：只辅助 Emby 刮削 `.strm`

审查原则：插件的价值只在 Emby 无法从 `.strm` 得到的数据上，能由 Emby 完成的工作不应被插件抢占或干扰。
对照最终现状：

- `MusicStrmLocalProvider.GetMetadata` 对非 `.strm` 路径直接返回空结果，不参与普通音频元数据；
- 插件不再注册 `IRemoteMetadataProvider`/`IRemoteImageProvider`，不参与在线元数据合并或封面图片下载；
- Provider 命中后只返回 `MetadataResult<Audio>`，不调用 `UpdateToRepository` 直写库，
  MusicAlbum/MusicArtist 关系由 Emby 合并保存；
- 旧库修复是设置页上的显式按钮动作，不挂在 Provider/扫描链路上，且删除条件保守。

这也是后续维护的约束：新增在线补全、图片、艺人或专辑写入逻辑时，
继续按 `.strm` 路径过滤并保持“返回结果给 Emby，不让 Provider 代 Emby 落库”。
封面交给 Emby 内置 MusicBrainz 图像获取器，选版也不使用 CAA 封面图数量决胜。
端到端验证使用的临时部署在验证后已恢复为原 `1.7.1.0`，
除条目 `1031` 的刷新时间外未对 Emby 媒体库造成持久变更。

## P2：可能导致选版错误

### 1. `HasExactTrackCount` 会漏掉 release 中未被本地消费的额外碟

位置：`MusicStrmExtract/Online/ReleaseLayoutMatcher.cs:46-78`

`MapLocalDiscsToMedias` 只要求每个本地碟组能找到覆盖它的 release media，不要求 release 的所有 media 都被消费；
`HasExactTrackCount` 也只比较 mapping 中的每一碟。

因此本地只有 `Disc 1`（13 轨）时：

- 13 轨单碟标准版：被判定为 exact；
- `media1=13 + media2=bonus` 的豪华版：也会被判定为 exact。

若同 RG 内两个版本同档（当时残余并列还可能交给 CAA 决胜），豪华版可能被误选；
若豪华版先出现而标准版不在同一档，旧 `TryResolveFromReleaseGroupAsync` 还可能直接 break，
标准版不会被继续检查。这不符合“标准版应优先于豪华版”的选版意图。
二次修复已移除 CAA 决胜，exact 命中按稳定分层直接返回。

建议：exact 判定额外要求 `mapping.Count == medias.Count`，不完整的本地碟集降级为 fallback；
补“本地只有主碟 + 标准版/豪华版都在候选”的测试。

### 2. 文件夹年份解析会把专辑标题里的年份当成发行年份

位置：`MusicStrmExtract/Online/AlbumSearch.cs:43-45,91`、`MusicStrmExtract/Online/JsonUtil.cs:42-51`

`SearchForTrackMapAsync` 直接把 `albumFolderName` 交给 `JsonUtil.ParseYear`，
而 `ParseYear` 使用 `Regex.Match` 取第一个四位年份：

- `"1989 (Taylor's Version) (2023)"` 得到 `1989`，而不是发行年份 `2023`；
- `"The 1975 (2013)"` 得到 `1975`，而不是 `2013`。

这会污染 RG 评分中的“年份贴近”排序层，使实际发行版本可能排在错误位置。

同族的 `CleanAlbumName` 问题：年份前后允许只有空格、没有括号或分隔符，
`"The 1975"` 会被清洗成 `"The"`，`"2001"` 会被清洗成 `null`。
如果目录不放发行年后缀，标题本身包含年份的专辑会直接搜索错误或跳过。

建议：

- 从文件夹名解析发行年份时，只取“位于末尾的年份后缀”，不要取标题里的第一个年份；
- `CleanAlbumName` 增加纯年份标题的回归测试，例如 `2001`、`The 1975`；
- 为 `ParseYear`/选版链路增加 `1989 (Taylor's Version) (2023)` 这类用例。

## P3：边界、并发与 UI 问题

### 1. 修复按钮进度与最终结果没有顺序保证

位置：`MusicStrmExtract/Ui/MusicStrmPageView.cs:122-134`

`Progress<string>` 在 `Task.Run` 内创建，服务器端没有可捕获的 UI `SynchronizationContext`，
`Report` 会异步投递到线程池。最终结果在 `Run` 返回后同步写入，
稍后到达的“正在删除/正在排队”旧进度可能覆盖“修复完成”或最终统计。

建议：改用串行执行的 `Action<string>`，或在最终状态写入前等待进度队列排空。

### 2. 修复服务未在刷新阶段继续防扫描竞态

位置：`MusicStrmExtract/Ui/StaleMusicAlbumRepairService.cs:149-176`

最后一次 `IsScanRunning` 检查在刷新队列构建前；`172-176` 行的刷新循环只检查取消，
不再检查扫描状态。扫描可能在最后一次检查之后、循环期间启动，使刷新与扫描并发执行。

建议：在刷新循环内继续检查 `IsScanRunning`，或把最终扫描检查放到 QueueRefresh 之前。

### 3. 修复服务覆盖不到“Audio 无 MBID 但已引用陈旧 MusicAlbum”的旧库

位置：`MusicStrmExtract/Ui/StaleMusicAlbumRepairService.cs:156-160`

刷新条件要求 `HasMusicBrainzAlbum(a)`。如果旧 Audio 只有 `AlbumId` 指向无路径、
无 MBID 的 MusicAlbum，该 Album 因被引用而不删除，Audio 又因无 MBID 不排队刷新，
最终返回“删除 0、刷新 0”且状态卡住。

建议：若“旧库修复”覆盖完全未刮削条目，应把“引用陈旧专辑但无 MBID”的 `.strm`
也纳入刷新；否则在 README/UI 中明确这一边界，并补对应测试。

### 4. 并发刷新同一专辑时可能重复跑完整 MB 查询

位置：`MusicStrmExtract/Providers/AlbumTrackMapLocator.cs:38-50`、
`MusicStrmExtract/Online/MusicBrainzApi.cs:71-90`

`AlbumTrackMapLocator` 在缓存 miss 后没有 per-key 单飞；`MusicBrainzApi` 在进入限流门前查缓存，
进门后不重查。若 Emby 对同一专辑多个 `.strm` 并发刷新，多个请求会重复执行完整专辑搜索，
只是被静态限流门串行化，仍有请求放大风险。

建议：对 album cache key 增加 async single-flight，或抢到限流门后重查 response cache。

### 5. recording 无艺人 MBID 时会把专辑艺人 MBID 错误写入曲目

位置：`MusicStrmExtract/Providers/MusicStrmLocalProvider.cs:192`

`track.ArtistMbid ?? album.AlbumArtistMbid` 在 recording 有独立艺人名但没有 ID 时，
会把专辑艺人的 MBID 写进 `MusicBrainzArtist`，可能让 Emby 把不同艺人实体错误关联。

建议：只有 `track.Artists.Count == 0`（曲目确无独立艺人信息）时才回退专辑艺人 MBID。

### 6. `StrmFileParser` 注释与实现/测试矛盾

位置：`MusicStrmExtract/Providers/StrmFileParser.cs:132-134,154,170-173`

注释声称 `comm={1,3,5}, reg={1..8}` 这类“部分交错”应映射到 `1/2/3`，
但实现只在等长奇偶交错时映射，实际和测试均按原始轨号返回。注释会误导后续维护。

建议：修正注释，或补上真正支持的部分交错语义并同步测试。

### 7. RG lookup 有 25 条上限，代码按“全量 release”处理

位置：`MusicStrmExtract/Online/MusicBrainzApi.cs:64`、
`MusicStrmExtract/Online/AlbumSearch.cs:119,142`

MusicBrainz lookup 的 linked entities 最多返回 25 条且按 GID 排序；
代码把 `GetReleaseGroupAsync` 的结果当作“该 RG 全部 release”来评分。
再叠加搜索回退只尝试 top-10 中的前 5 个候选，极端情况下正确版本可能完全不在候选集中。

建议：至少把上限写入注释，必要时用 `/release?release-group=...` browse 分页补齐，
并扩大搜索回退候选覆盖范围。

### 8. 分析器资源释放提示

- `MusicStrmPageView` 持有 `CancellationTokenSource`，但类型未实现 `IDisposable`
  （`MusicStrmExtract/Ui/MusicStrmPageView.cs:13-19`），依赖 Emby 一定调用 `Cancel` 来释放；
- `RequestRateLimiter` 持有 `SemaphoreSlim`，未实现 `IDisposable`
  （`MusicStrmExtract/Online/RequestRateLimiter.cs:13`），当前为静态进程级实例，影响较低。
